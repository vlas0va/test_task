# Avito candidate generation — модель 1 + модель 2 + модель 3

## Результат

На реальном benchmark: **Recall@50 = 0.552** (полный ансамбль моделей 1+2+3).
Офлайн-прокси на train (см. `evaluate_offline.py`/`03_train_reranker.ipynb`) даёт
более консервативную оценку (~0.40-0.41) — реальный скор на benchmark оказался
заметно выше, так что офлайн-цифры стоит воспринимать как нижнюю границу, а не
точный прогноз (подробнее — в разделе "Грабли" ниже).

## Структура решения

- **Модель 1** — BM25 (лексический поиск, своя векторизованная реализация на
  scipy sparse) + гео-буст. Самостоятельный рабочий baseline, см.
  `generate_submission.py` — можно сдавать уже им одним, если не успеваете
  дальше.
- **Модель 2** — bi-encoder эмбеддинги (`intfloat/multilingual-e5-base`).
  **e5-бэкбон заморожен** (не дообучается) — вместо полного файнтюна обучается
  только маленькая голова `DoubleGeGLUHead` (два GeGLU-блока с residual +
  LayerNorm, см. `custom_head.py`) поверх него, контрастивным InfoNCE-лоссом
  (эквивалент `MultipleNegativesRankingLoss` из sentence-transformers) на
  реальных кликах из `train.parquet`. Почему так, а не полный файнтюн — см.
  раздел "Почему заморожен e5" ниже.
- **Модель 3** — LightGBM-ре-ранкер (lambdarank) поверх признаков от моделей
  1+2 и дополнительных (гео, категория, рейтинг, цена, длины текста) —
  учится сам комбинировать сигналы вместо ручных весов
  (`"BM25 + 40*location_match"`, как в модели 1 отдельно).

## Почему заморожен e5, а не полный файнтюн

Обучение делалось на ноутбуке с 6 ГБ VRAM (RTX 3060 Laptop) — полный файнтюн
`e5-base` (~278М параметров) с AdamW на таком объёме памяти упирался в OOM
или уходил в очень медленный режим (VRAM переполнялась в shared/системную
память). Решение: заморозить e5 целиком (`requires_grad=False`) и обучать
только голову `DoubleGeGLUHead` сверху.

Раз e5 заморожен и детерминирован, его выход не меняется от эпохи к эпохе —
поэтому эмбеддинги считаются **один раз** и кэшируются на диск как `.npy`
(`np.load(..., mmap_mode="r")` — не грузятся целиком в RAM, читаются по
требованию), а голова обучается ручным циклом (AdamW + линейный warmup +
ручной InfoNCE через косинус + cross-entropy) поверх этого кэша — без единого
forward/backward через сам трансформер во время обучения. Это на порядки
быстрее и не упирается в VRAM.

## Ноутбуки (основной способ запуска)

Три интерактивных ноутбука, разбитые по шагам — предпочтительнее голых
`.py`-скриптов ниже, так как позволяют проверять промежуточные результаты и
не терять уже посчитанное при сбоях (см. "Грабли"):

1. **`01_train_biencoder.ipynb`** — модель 2: кэширует эмбеддинги e5+pooling
   (`./embed_cache/*.npy`), обучает `DoubleGeGLUHead` поверх кэша с
   чекпоинтингом каждой эпохи (`./head_checkpoints/epoch_N`) и val recall@50,
   в конце собирает и сохраняет лучшую модель в `./biencoder_finetuned`.
2. **`02_embed_and_retrieve.ipynb`** — модель 2 применение: FAISS top-300 по
   косинусу. Гоняется **дважды** с разным конфигом (train-режим для
   обучения/оценки ре-ранкера, benchmark-режим для финального сабмита) — см.
   переключатель в конфиг-ячейке. Кэширует эмбеддинги и результаты
   FAISS-поиска на диск (`./retrieve_cache_train` / `./retrieve_cache_benchmark`),
   так что при падении (memory/крэш) повторный запуск не считает всё заново.
3. **`03_train_reranker.ipynb`** — модель 3: обучает LightGBM на признаках из
   `features.py`, печатает сравнение Recall@50 (baseline BM25+гео vs
   LightGBM) и feature importance, сохраняет `reranker_lgb.txt`.

Порядок: **01 → 02 (train) → 03 → 02 (benchmark) → `generate_final_answer.py`**.

## Файлы

| Файл | Что делает |
|---|---|
| `text_prep.py` | подготовка текста (отдельно для BM25 и для эмбеддингов) |
| `bm25.py` | своя векторизованная реализация BM25 (scipy sparse) |
| `custom_head.py` | `DoubleGeGLUHead` — обучаемая голова поверх замороженного e5 |
| `features.py` | признаки пары (запрос, объявление) для ре-ранкера |
| `evaluate_offline.py` | офлайн-валидация BM25-каналов на train.parquet |
| `generate_submission.py` | модель 1 целиком, готовый `answer.csv` без моделей 2/3 |
| `train_biencoder.py`, `embed_and_retrieve.py`, `train_reranker.py` | те же модели 2/3, но как обычные `.py`-скрипты (устаревшая версия без mmap-кэша головы — предпочтительнее ноутбуки выше) |
| `summarize_with_llm.py` | опционально: LLM-суммаризация объявлений через Ollama |
| `generate_final_answer.py` | сборка моделей 1+2+3 в финальный `answer.csv` |

## Грабли, на которые уже наступили — чтобы не наступать снова

- **`trust_remote_code=True`** обязателен при загрузке `./biencoder_finetuned`
  через `SentenceTransformer(...)` (везде, где грузится эта папка) — модель
  ссылается на кастомный класс `DoubleGeGLUHead`, sentence-transformers
  требует явного согласия на выполнение стороннего кода.
- **`intfloat/multilingual-e5-*` требуют префиксы** `"query: "` / `"passage: "`.
  В коде это определяется по имени модели (`is_e5_model`) — но для локальной
  папки `./biencoder_finetuned` имя не содержит "e5", поэтому детект идёт по
  ОТДЕЛЬНОЙ переменной `BASE_MODEL_NAME`, которую нужно вручную держать в
  синхроне с тем, что стояло в `01_train_biencoder.ipynb` при обучении.
- **При смене текста для эмбеддингов (maxlen объявлений и т.п.) или базовой
  модели — обязательно чистите кэши**, иначе код молча переиспользует старые
  эмбеддинги/кандидатов и правка не даст эффекта: `./embed_cache`,
  `./head_checkpoints`, `./biencoder_finetuned`, `./retrieve_cache_train`,
  `./retrieve_cache_benchmark`, `embed_candidates_train.parquet`,
  `embed_candidates.parquet`, `reranker_lgb.txt`.
- **Кодирование объявлений (items) сильно дороже запросов (queries)** — тексты
  объявлений заметно длиннее, при большом батче на 6ГБ VRAM легко улететь в
  shared memory и просесть в скорости в десятки-сотни раз. В коде уже разведены
  `BATCH_SIZE_QUERY`/`BATCH_SIZE_ITEM` (меньший батч для items) + fp16
  (`model.half()`) — не сводите их обратно к одному общему батчу.
- **Сборка "плоской" таблицы кандидатов (query × TOP_N) — только векторизованно
  (numpy), никогда Python-циклом с `.append()`** — на ~350к запросов × 300
  кандидатов это ~100+ млн строк, Python-цикл валит процесс по памяти
  (`MemoryError`) и/или крэшит VS Code целиком.
- **Джойн эмбеддинг-скоров в `features.py` — через `.reindex()` по готовому
  MultiIndex `embed_lookup`, а не через `.merge()`** — `.merge()` каждый раз
  пересобирает и перехэширует всю ~100-миллионную таблицу кандидатов заново,
  это тоже валит процесс по памяти.
- **Офлайн Recall@50 — консервативная и не всегда репрезентативная оценка**:
  и в 01 (val split), и в 03 (`eval_uids`) отложенная выборка — случайные
  запросы ИЗ TRAIN, то есть отражает распределение train, а не benchmark.
  Например, `search_category == 0` — почти не встречается в train (0.01%), но
  занимает ~9% запросов в benchmark — офлайн-метрики о таких сегментах
  практически ничего не говорят. Реальный скор на benchmark может (и оказался)
  заметно отличаться от офлайн-оценки.
- **Не смешивайте эмбеддинги разных моделей усреднением с фиксированными
  весами** (например 0.33/0.33/0.33) — это разные векторные пространства.
  Правильно: либо одна эмбеддинг-модель для модели 2, либо отдельная колонка
  `embed_score_modelX` на каждую модель в `features.py`, и пусть LightGBM сам
  решит веса.
- **`CANDIDATE_POOL=300`** — ширина первой стадии (BM25) для обучения/оценки
  ре-ранкера. Разумный баланс между recall и скоростью, подбирался эмпирически.
